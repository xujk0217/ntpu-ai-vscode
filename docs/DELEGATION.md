# Agent 自動分工

分工設計參考 [OpenAI 官方多 Agent 文件](https://developers.openai.com/api/docs/guides/agents-api/multi-agent) 的原則：明確界定獨立工作、分開脈絡、保留父任務整合，將短小與相依步驟留在主 Agent。這個專案的模型請求沿用 NTPU AI 網頁瀏覽器與既有工具迴圈。

啟用平行工作時，複雜的實作、調查、研究與審查要求會先經過主機端的分工評估，包含「修復登入」「修改記憶功能」等簡短要求。主 Agent 必須回傳 `kind: "delegation"`，列出可獨立進行的工作，或引用已成功讀取的來源，說明工作確實只涉及狹小範圍或具體相依性。泛用「一個 Agent 比較快」不能略過分工。

若回覆只有泛用理由，或模型連續兩次未遵守評估格式，主機會在能力、名額與共用預算允許時，啟動一個真正的唯讀查證子任務：本機任務盤點相關既有入口、測試與回歸風險；研究任務查證官方來源。主 Agent 同時繼續獨立工作，結束前收集實際結果；不能用虛構分工紀錄當成有開子 Agent。已根據證據保持單 Agent，後續探索出不同來源時，可再評估一次。恢復已有分工證據的檢查點不會自動重派同一批工作。

簡短問答、單一步驟工作、Ask 模式、已取消任務、服務限制或預算不足時保留單一 Agent。分類採本機規則，並非完整的語意理解；分工評估會再次確認實際工作是否相依。使用者不必替每個子任務另外開啟聊天。

分工評估範例：

```json
{
  "kind": "delegation",
  "tasks": [
    {
      "title": "登入流程證據",
      "role": "explore",
      "request": "讀取登入管理程式，找出可能失敗的階段。",
      "expectedOutput": "回報檔案行號、錯誤傳遞路徑與可確認或排除的假設。",
      "independent": true
    },
    {
      "title": "回歸範圍調查",
      "role": "review",
      "request": "檢查現有 localhost fixture 與登入測試覆蓋範圍。",
      "expectedOutput": "列出既有測試、缺少情境與適合主 Agent 補上的驗證步驟。",
      "independent": true
    }
  ]
}
```

主 Agent 繼續處理獨立的實作工作，結束前必須收集實際子任務結果。子任務只可讀取、搜尋、研究或審查；主機工具白名單禁止子任務寫檔、執行 shell、再開子任務或任意呼叫 MCP。依賴尚未完成修改的驗證不能假裝成可獨立工作。

每個子任務最多六輪，父子共享同一個模型輪數、請求頻率與自適應併發排程。主機保留至少三個模型請求供主 Agent 整合與驗證，新增子任務至少要有兩輪可用，資源不足時減少分派或由主 Agent 完成。同時最多四個子任務，背景命名工作也占用名額；每個父任務仍受現有總子任務數限制。更多子任務不代表可以跳過校方的排隊、登入、429 或用量限制。

一般子任務失敗不會阻擋其他不同的獨立工作。同一失敗內容以正規化後的 request 比對，不能只改標題、角色、空白、大小寫或標點重開對話。主 Agent 不得改寫同一需求來規避重試限制；必要的一般失敗可用原始 ID 呼叫 `retry_task` 一次，記錄具體理由及連結，原始失敗證據會保留。登入、服務限制、取消、本機保存失敗或預算不足禁止重試。程式不能可靠判斷所有語意相同的改寫，因此仍保留整體任務數、預算與服務限制作為上限。

子任務回覆不再截成 10,000 字。完整結果與已接收的分段保存在本機，主 Agent 收集結果可取得完整內容。收到可保存的段落後先等待本機持久化，之後才繼續生成；串流中的尚未完成文字另標記為部分內容。一般中斷不會覆蓋已保存的結果。若本機保存失敗，任務標記失敗並保留校方對話供恢復，不能把未保存或未完成的內容當成成功。安全遮蔽規則仍適用，憑證不會因完整保存而被記錄。
